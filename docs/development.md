# Build, extend and validate

## Prerequisites

This build currently supports Linux x86-64. It uses the sibling Tetrodotoxin
module's Clang toolchain and canonical Perimortem/TTX targets. That toolchain
currently selects C++26 for native C++, with RTTI enabled at the Godot extension and script-provider boundaries. The lab contains no separate CMake or SCons build step.

| Dependency | Current configuration |
| --- | --- |
| Tetrodotoxin | Sibling `../tetrodotoxin`, selected by `local_path_override` in MODULE.bazel. Verified cleanup baseline: `e6f236e8b4092c1b32cb4c44ed265bfe9dca7da1`. |
| Bazel | Verified with 9.2.0. Builds TTX dependencies as part of this module. |
| Godot | Addon declares minimum 4.5; this pass runs on 4.7.2. |
| godot-cpp | Pinned and generated by [repository rules](../third_party/repositories.bzl), using Python 3. |
| FFTW | Single-precision `fftw3f`; `FFTW_ROOT` defaults to `/usr`, expecting `include/fftw3.h` and `lib/libfftw3f.so`. |
| CUDA | `CUDA_ROOT` defaults to `/opt/cuda`, expecting `include` and `lib64`, including NVRTC and cuFFT. Not needed for `--cpu`. |
| NVIDIA driver/GPU | Required for actual GPU execution. This pass uses an RTX 5070 and driver 610.57.04. |
| Shell tools | Bash, Python 3, tar and ripgrep; ffmpeg additionally for capture. |

A distribution with different library directories needs the corresponding SDK
rule adapted. The addon tar does not bundle FFTW, Godot, CUDA SDK libraries or the
NVIDIA driver. CUDA's current search path includes its configured SDK location.
Fresh-machine portable distribution remains a release-review target.

## Workflows

Run from the repository root:

```sh
tools/run-lab.sh
tools/check.sh
```

Both default to release and actual CUDA execution, alongside GDScript and native CPU. `--cpu` builds the CPU and GDScript paths without the CUDA provider. `CONFIGURATION=debug` uses the same paths in a debug configuration.
`tools/check.sh --no-visual` runs GPU/native/installed checks without requiring a
rendered window. `tools/capture-demo.sh` requires a working display and GPU, drives
the actual scene test, and refreshes `docs/lab.gif` and `docs/lab.png` from its
viewport. Captured media is not a synthetic rendering of the UI.

The individual build targets remain usable:

```sh
bazel build //:addon --config=release --config=cuda
bazel test //tests:image_check --config=release --config=cuda
bazel build //providers/cpu:cpu_provider --config=debug
bazel build //providers/cuda:cuda_provider --config=debug
```

Omit `--config=cuda` for a CPU-only addon or native test. The addon output is
`.bin/bin/godot_ttx.tar`. Normal Bazel parallelism is used.

The [installer](../tools/install-addon.sh) accepts any directory containing a
`project.godot` and installs under `addons/godot_ttx`. It removes a stale CUDA
provider when installing a CPU-only archive. Keep the extension, shared runtime,
provider modules and `.gdextension` file together. Restart any editor that has
already loaded these libraries; their callable tables borrow executable code.

The scripts use this fresh-import synchronization workaround:

```sh
godot --headless --editor --path /absolute/path/to/project --frame-delay 1000 --quit
```

Immediate fresh `--editor --quit` has previously aborted in Godot's editor
shutdown. The delayed command is the established workaround, not an engine fix.
Runtime execution needs no delay. The checks also run the ordinary scene through
startup and shutdown: that separately covers native owners constructed by the UI.

## Use the addon elsewhere

The default provider is CPU. Set `TTX_IMAGE_PROVIDER=cuda` before launching Godot,
or set an individual TtxImage Resource's `provider` property to `cpu`, `cuda`, or a
shared-library path. That selection applies to the next `set_rgba8`; changing it
alone does not rewrite an existing source. Failed publication preserves the prior
source and reports its error.

`gdscript` selects the bundled script factory. A `.gd` or `.gdc` path selects a
custom factory script. An already constructed RefCounted factory can instead be
supplied with `source.set_provider_object(factory)`. Either setter replaces the
previous selection; the next `set_rgba8` attempts publication. Calling
`set_provider(path)` clears an object selection. Failed publication keeps the
previous source. Publication and provider setters reject calls made from inside
an active image observation; they are available again after that synchronous
call returns. `get_provider_statistics()` exposes the existing diagnostic counters
for lab tests, separately from image identity.

A Sprite2D can use the installed API as follows:

```gdscript
extends Sprite2D

func _ready() -> void:
    var pixels := Image.create(256, 128, false, Image.FORMAT_RGBA8)
    pixels.fill(Color(0.2, 0.4, 0.8, 1.0))
    var source := TtxImage.new()
    if not source.set_rgba8(256, 128, pixels.get_data()):
        push_error(source.get_error())
        return

    var inverted := source.invert()
    if inverted == null:
        push_error(source.get_error())
        return

    var observed := inverted.read_pixels()
    if observed.is_empty():
        push_error(inverted.get_error())
        return

    centered = false
    texture = ImageTexture.create_from_image(
        Image.create_from_data(256, 128, false, Image.FORMAT_RGBA8, observed))
```

The full three-provider example is [demo/lab.tscn](../demo/lab.tscn). Its source Resources
hold configuration, [branch.gd](../demo/branch.gd) performs image operations and
[lab.gd](../demo/lab.gd) owns presentation. This keeps the same client pipeline
visible instead of duplicating it for the GPU panel.

## Add a provider

Start with [contracts/provider.h](../contracts/provider.h) and
[contracts/image.h](../contracts/image.h). They define module entry, owned factory,
image control operations and callable carriers. The CPU
[factory](../providers/cpu/provider.cpp) and [Image](../providers/cpu/image.cpp)
are the smallest production example.

The GDScript [factory](../providers/gdscript/provider.gd) and
[image](../providers/gdscript/image.gd) provide an implementation inside Godot.
Their [native bridge](../providers/gdscript/image.cpp) publishes the same tables.
See [the script authoring contract](provider-patterns.md#script-authoring) before
adding another script implementation.

A provider supplies image creation, lifetime control and a Semantic Query that can
bind Thunk. It fulfills supported operation UUIDs after checking the requested
convention and table representation, then returns matching functions with its
opaque receiver. Pixels publish their own Data Representation and supported
transport. Neither native object layout nor payload storage leaks into that ABI.

The optional [Providers::Image](../providers/image.hpp) helper publishes these
common tables for a C++ owner. Its fulfillment result preserves Core's complete
failure vocabulary. Adding an optional operation changes a provider's fulfillment
inventory; it does not add another mandatory base virtual method. A different
language can implement the C contract without this helper.

Put implementation code and SDK dependencies in a separate Bazel package under
`providers/`, export a shared-library target, and configure a source with the module
path. Run the dependency boundary check to ensure the new provider does not gain
an accidental dependency on the host graph or another backend. The current helper
uses one shared Perimortem runtime across loaded modules; independent runtimes need
their own explicit allocation and lifetime agreement.

## Add an operation

Begin with the questions the operation must answer: input meaning, result,
ownership, possible failures and numerical guarantees. Use the typed
[Invert](../contracts/invert.hpp), [Convolve](../contracts/convolve.hpp) and
[Composite](../contracts/composite.hpp) contracts as examples.

1. Define its C carrier, callable signature and contract UUID. A UUID denotes its
   behavioral agreement, not only the byte size of the function table.
2. Add its typed C++ Handle and a provider implementation. Fulfillment returns
   Unsupported where the capability is absent; rejection must remain rejection.
3. Publish the operation with its typed factory in
   [Standard](../operations/standard.cpp). Existing argument families are unary,
   kernel and second-image input; each factory captures that exact contract.
4. For a new argument family, add its explicit Godot conversion and typed host
   invocation. Keep that policy at the host boundary instead of teaching Data
   image semantics.
5. Add an independent result oracle and failure/lifetime checks. The
   [Echo probe](../tests/echo.hpp) shows how to test a second contract of the same
   host argument family without accidentally invoking the old signature.

Published UUID meanings must remain stable when later versions add capabilities.
This lab is under review before 1.0; it does not yet establish a frozen release ABI.

## Acceptance and proof boundaries

| Check | What it exercises |
| --- | --- |
| `tests:image_check`, CPU | Independent pixel oracles, source preservation, invalid kernels, snapshots, dependency changes, exact typed invocation and failure propagation. |
| `tests:image_check`, CUDA | Actual device execution, mixed-provider composition, expected uploads/downloads, FFT plan reuse and final image allocation release. |
| `tests/godot_check.gd` | The unchanged client API under all three installed provider selections. |
| `tests/gdscript/check.gd` | Existing-object admission, script retention/release, delegated Callables, refusal, malformed results, and mixed native/script operations. |
| `tests/visual_check.gd` | Real scene/buttons/textures, retained filter Resources after overlay changes, replacement after source changes. |
| `tools/check-boundaries.sh` | Provider build closures exclude each other and the host/Concept graph; only GDScript depends on Godot. |
| Ordinary headless scene | Startup and destruction of the actual application's native owners. |

Run the GDScript oracle directly after installation:

```sh
TTX_IMAGE_PROVIDER=cpu godot --headless --path demo \
  --script res://addons/godot_ttx/godot_check.gd
TTX_IMAGE_PROVIDER=cuda godot --headless --path demo \
  --script res://addons/godot_ttx/godot_check.gd
TTX_IMAGE_PROVIDER=gdscript godot --headless --path demo \
  --script res://addons/godot_ttx/godot_check.gd
```

GPU-required tests fail if the provider/device is unavailable. A CPU-only pass is
reported separately, and skipping the visual window makes no rendered-output claim.
The visual test compares unquantized image bytes; GIF palette conversion affects
presentation only.

When foundation code changes, the sibling repository's Data and Semantic focused
suites remain additional gates. Their loaded C fixtures cover the foreign language
boundary independently of these C++ image providers. Keep dispatch allocation
instrumentation isolated in its existing test executable, rather than adding
process-wide measurement hooks to this lab.

## Reproduce the provider comparison

```sh
bazel run //tests/performance:mechanics --config=release --config=cuda
godot --headless --path demo --script "$PWD/tests/gdscript/benchmark.gd" -- --cuda
```

Run these after installing the release addon as described above. Omit
`--config=cuda` from the native command and `--cuda` from the script command for
the CPU/GDScript comparison. The native executable measures direct dispatch,
fulfillment, retained invocation, fresh graph construction, cached observation
and pixel-form compilation separately. It loads the real CPU and optional CUDA
providers and keeps its allocation counters out of the addon. CUDA operation
rows include device allocation, kernel execution and synchronous completion.

The script benchmark warms each backend, then creates a fresh operation on every
iteration. Each `TtxImage.invert()` or `convolve()` constructs a graph Call, fulfills
its binding, produces an image and creates a Godot Resource. This is different
from repeatedly invoking one retained binding. Final pixel readback is outside
the operation timer and has its own `readback_us` field.

Inversion scales through 2048×1024. Convolution includes 1024×512 and 2048×1024
with 63×63 kernels, while explicitly skipping impractical spatial GDScript cases.
Native batches use at least 50 inversions or 10 convolutions after three warmups.
The script implementations use smaller batches. `MEASURE` records include the
exact path, dimensions, kernel, warmup count and sample count. Returned pixels
must agree exactly for inversion and within one byte for convolution.

See [the measurements and their interpretation](performance.md), including why
backend warmup does not mean cached TTX fulfillment. Direct GDScript and GDScript
through TTX use the same algorithm. Native convolution uses FFTW/cuFFT, so that
comparison includes algorithm and resource-lifetime choices. Timings remain
observations, never pass criteria.

## Run the scalar callable example

```sh
bazel test //tests/sampling:check --config=release --config=cuda --test_output=all
godot --headless --path demo --script "$PWD/tests/gdscript/sampling.gd" -- --cuda
```

The addon provides `TtxSampler` beside `TtxImage`. Its configured function owns
one module and fulfilled callable, and repeated calls return integers directly.
Both checks are included in `tools/check.sh`. Omit the CUDA flags for CPU-only
validation. [Sampling](sampling.md) explains the mathematical contract, ownership,
partitioned work and how the timing differs from an image Resource operation.
